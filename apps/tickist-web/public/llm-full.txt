# Tickist: full LLM reference

## 1. Purpose and audience

Tickist is an open-source personal and collaborative work-management application. Its design goal is to turn scattered commitments into a calm, actionable workspace. A user captures incoming work in a single Inbox, assigns work to projects, sets a priority and schedule when useful, and uses dashboard views to decide what to do next.

The product is not a public content site or a generic file store. It is an authenticated workspace. Users own their data and may share individual projects with collaborators.

## 2. Core product model

### Projects

- Each user has one Inbox project for uncategorised tasks.
- Projects can be active, nested under another project, or organised into special sidebar groups such as Someday/Maybe, routine reminders, weekdays, and future work. A selected project task list includes that project's tasks and every nested descendant by default. If descendants exist, independent checkboxes beside the selected project and each descendant temporarily include or exclude that project's own tasks; changing the selected project resets all of them to included.
- Projects have a name, description, colour, icon, task-view preference, and defaults for task creation. Branding provides a searchable catalogue of 151 Lucide icons.
- A project owner can invite collaborators. Members can accept or decline invitations; accepted members can work in the shared project according to their role.

### Tasks

- A task belongs to a project or the Inbox.
- Core fields include name, description, priority, due date/time, status, task type, pinned state, estimated/spent time, recurrence, tags, assignees, subtasks, and reminders.
- The Extra tab in task editing includes a compact read-only history with the creation timestamp and latest modification timestamp. This history is not shown while creating a task.
- Task-card overflow action menus are coordinated by their task list. Opening a second task menu closes the previously open menu, and selecting the same trigger again closes that menu.
- Assignee selectors in accepted shared projects use member display labels rather than internal user IDs. Tasks created through either the full composer or quick project entry are assigned to their creator by default when the selected project is shared; users may still choose another member or leave the task unassigned.
- Priorities are A, B, C, and normal. Task types include normal, next action, and need info.
- Completion is a first-class activity: when `is_done` changes to true, the database records `when_complete`; reopening a task clears that value. Task cards show the completion date when completed tasks are included by the active filter.
- Tasks can be suspended indefinitely or until a future date and time. The time defaults to local `00:00` when the user selects a resume date without changing it. Suspended tasks use `is_active=false`; `suspend_until=null` means indefinite suspension. A due suspension is resumed in Postgres within approximately one minute, and the browser treats an expired timestamp as active while that update completes.
- Project task views can filter all, active open, suspended, or completed tasks. The active-open filter excludes suspended work. Suspended cards show a non-interactive pause indicator instead of a completion checkbox, and the project header counts suspended, incomplete tasks across the currently included project hierarchy. Clicking that count selects the suspended-task filter.
- Task views can sort by priority, due date, creation date, modification date, or alphabetical name.
- Recurring-task completion resets the next occurrence instead of treating the task as permanently finished.

### Organization and focus

- The dashboard groups today, overdue, pinned, next-action, and need-info tasks; suspended work is excluded from these active-work groups.
- The task tree and sidebar task counts exclude suspended work until it resumes.
- The tag view filters by one or more tags, supports OR/AND matching, can include completed work, and has the same primary sorting choices as project task lists.
- Statistics report completion, late completion, overdue work, and inactive projects for a selected time window.

### Account and portability

- Account settings include profile/avatar handling, password changes, notification preferences, backup/restore, and API-token management.
- Export/import uses stable IDs and timestamps to support resilient migration and conflict handling.
- Placeholder text uses one muted slate colour across application forms in both themes, keeping hints visually secondary to entered values.

### MCP integrations

- Authenticated clients manage projects, tasks, and tags exclusively at `https://mcp.tickist.com/mcp`; the main application Worker does not expose or proxy `/mcp`.
- The primary protocol is stateless MCP `2026-07-28`: every request carries its protocol version and client capabilities, and matching HTTP routing headers are required. `server/discover` reports the server identity and capabilities and advertises only the modern `2026-07-28` revision; legacy negotiation remains separate.
- Initialization-based MCP `2025-06-18` remains supported for existing clients. The endpoint does not use protocol sessions in either era.
- Modern results include `resultType`, deterministic tool discovery, required cache hints, text content, and object-shaped structured JSON content. Requests and tool arguments are validated before handlers run. Header mismatches, unsupported versions, notifications, and unknown methods use the status and JSON-RPC behavior defined by the selected protocol era.
- OAuth 2.1 uses authorization code with PKCE through Supabase Auth. Its access-token hook preserves the standard `authenticated` audience and adds the exact MCP resource audience. The Worker publishes RFC 9728 metadata, supports dynamic client registration for compatibility, cryptographically verifies access-token signatures against Supabase Auth signing keys, and then checks issuer, MCP audience, expiry, subject, `tickist_mcp = true`, and the signed `tickist_mcp_scopes` claim. Supabase PostgREST enforces user-scoped RLS for data access. Consent is handled at `/auth/oauth/consent`; users list and revoke grants at `/app/settings/connected-apps`.
- Tickist's Supabase OAuth server is reserved for MCP clients. Supabase accepts the standard `openid` scope; the access-token hook supplies all six project, task, and tag tool permissions in `tickist_mcp_scopes`. Personal tokens retain their independently selected `projects:*`, `tasks:*`, and `tags:*` scopes.
- OAuth tools use the public Supabase publishable key and the user's Bearer token, so RLS authorizes owners and accepted project members. The MCP Worker has no service-role credential. Tool permissions are enforced before handlers, and mutations write payload-free user audit records.
- Existing hashed `tk_` personal tokens retain their scopes and are temporarily forwarded to the old Edge Function. That function is a compatibility backend, not a second independently maintained MCP catalogue, and is retired after a separately approved token transition.
- The authenticated production MCP smoke sequence is temporarily disabled by default. It can be enabled with the GitHub Actions repository variable `ENABLE_MCP_OAUTH_SMOKE=true`, and its credentials are scoped only to the conditional smoke steps.
- Host, Origin, CORS request headers, strict UTF-8 JSON, actual body size, request identifiers, arguments, and tool names are validated before data access. A dedicated Cloudflare binding limits MCP POST requests per hashed connecting address and does not trust unverified Bearer values as limiter keys. Credentials and user payloads are not logged; client-visible failures omit database diagnostics, and all MCP Worker responses are noindex.

| `/auth` | Public | Sign in. |

Routes under `/app/**` are private and must not be listed in the public sitemap. Authentication pages are transactional routes, not content intended for search indexing.

The bottom of the public landing page introduces Spendist, a related open-source application for tracking spending, recurring payments, and everyday personal finances, and links visitors to `https://spendist.app/`.

### Public blog

- The public blog is implemented in `apps/tickist-web/src/app/features/blog/` and is available without authentication.
- `apps/tickist-web/content/blog/` is the repository-owned Markdown source. `en` and `pl` each own separate articles and `categories.json`. There is no translation key, shared article database, or automatic localization between editions.
- The first release has empty post registries. There is no CMS, administration panel, database-backed publishing flow, or comments.
- `tools/scripts/generate-blog-content.mjs` validates front matter, renders and sanitizes Markdown, calculates reading time, and generates the Angular content registry, sitemap, robots rules, and per-locale RSS feeds. `npm run blog:check` rejects stale generated artifacts.
- New Markdown defaults to `draft: true`; drafts are validated but excluded from public articles, sitemap, and RSS. `draft: false` is an explicit publication action.
- Published posts are available at `/{locale}/blog/{slug}` with responsive article rendering, table of contents, category and tag navigation, native/link sharing, canonical and social metadata, and `BlogPosting` JSON-LD. Category archives and pagination use the same generated registry.
- The Cloudflare Worker injects generated route-specific metadata into initial SPA HTML and applies security headers. Angular mirrors that metadata after client navigation.
- Social sharing belongs on public article pages once articles exist. Use only the article's canonical HTTPS URL. Do not add comments without a separate moderation and privacy design.

## 4. Data and security model

- Supabase Auth identifies the user.
- Postgres stores projects, tasks, tags, memberships, reminders, notifications, preferences, API tokens, and email-outbox data.
- Row Level Security is the authorization boundary. A user may access their own resources and project data they are allowed to access through membership.
- The browser receives only a Supabase publishable key. `SUPABASE_SECRET_KEY`, internal worker secrets, AWS credentials, and database credentials remain server-side.
- Database migrations are ordered files in `supabase/migrations/`. Schema changes must be backward-compatible and additive whenever production clients may still run older code.

## 5. Notifications and automation

Tickist uses an outbox pattern for application email. The browser or a scheduled worker queues an email; a protected worker sends it through AWS SES and records its status.

Important Edge Functions:

- `task-reminder` and `task-reminder-runner`: create and process task reminders.
- `routine-runner`: processes routine-reminder work.
- `project-update` and `project-invite`: support shared-project changes and invitations.
- `notification-digest-runner`: queues daily and weekly digests from notification preferences.
- `enqueue-notification`: authenticated endpoint for adding an application email to the outbox.
- `send-emails`: internal-secret-protected batch sender using AWS SES.
- `tickist-mcp`: temporary compatibility backend for existing hashed personal API tokens.

Schedulers and secrets are production infrastructure. Never expose an internal secret or an email-outbox payload to an unauthenticated client.

Postgres also schedules `resume_due_tasks()` every minute through `pg_cron`. The function activates incomplete tasks whose `suspend_until` timestamp has arrived and clears the consumed timestamp; it is not executable by browser roles.

## 6. Technical architecture

```text
Browser (Angular 22)
  ├─ Supabase Auth / PostgREST / Realtime / Storage
  │    └─ Postgres with RLS and migrations
  └─ Edge Functions
       └─ AWS SES for application email

Cloudflare Workers
  ├─ tickist-app: Angular assets, /env.js, and temporary /mcp proxy
  └─ tickist-mcp: MCP HTTP, health, and OAuth metadata
```

The codebase is an Nx workspace. `apps/tickist-web` is the Angular app, `apps/mcp` is the dedicated MCP server, `libs/data-access/tickist` is its RLS-backed data layer, and `apps/tickist-web-e2e` contains Playwright journeys. Unit tests use Vitest. Production uses separate application and MCP Cloudflare Workers.

## 7. Local development and test safety

- `npm run start` ensures the local Supabase project is running, then serves Tickist on port 4200.
- Local Supabase defaults to API port 54321, Postgres 54322, Studio 54323, and Inbucket 54324.
- E2E uses `SUPABASE_E2E_DB_URL` and resets that database in setup and teardown.
- E2E refuses to reset a database matching `SUPABASE_REMOTE_DB_URL`. It also refuses the regular local development database unless the developer explicitly sets `E2E_ALLOW_LOCAL_DB_RESET=true`; that exception is limited to localhost.
- The standard CI browser command is `npx nx e2e tickist-web-e2e -- --project=chromium`.
- `npm run demo:seed` validates a deterministic English demo dataset without connecting to Supabase. The marked Maya Chen account contains 30 projects, 200 tasks, and exactly 40 completed tasks; applying it requires an administrative secret, and remote writes require a matching project reference plus explicit confirmation.
- `npm run db:backup:remote` creates an authenticated, encrypted local disaster-recovery archive containing logical database, Auth, migration and Storage data plus physical Storage objects. The tool verifies the complete archive after creation and never automates destructive restore or retention deletion.

## 8. Public metadata and documentation policy

- `robots.txt` and `sitemap.xml` live in `apps/tickist-web/public/` and are deployed as root assets.
- The generated sitemap contains only public, indexable pages: the landing page, both blog indexes, published articles, populated category archives, and required pagination routes. Drafts never appear.
- `llm.txt` is the concise LLM discovery file; this file is its complete reference.
- Repository knowledge for coding agents lives in the root `doc/` directory. Read `doc/README.md` before changing a documented area.
- When a feature changes, update the relevant `doc/` page, `llm.txt`, and `llm-full.txt`. When a public route changes, update `sitemap.xml` and `robots.txt` in the same change.
